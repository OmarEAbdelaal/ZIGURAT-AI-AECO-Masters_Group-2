## 2. PII Handling (Privacy)

| Field | Entry |
|---|---|
| **Faces / people present?** | Incidental only. The subject of every image is a building exterior. Pedestrians and vehicles appear in street-level photographs the way they appear in any street photograph. |
| **Licence plates present?** | Incidental, same basis. |
| **Protection strategy** | **Data minimisation applied at the class contract.** There is no `person` class, no `vehicle` class, and no tracking, re-identification or counting of either. The model is structurally incapable of identifying a person: nothing in its output space refers to one. Faces and plates that survive in training imagery are blurred using Roboflow's blur augmentation before any dataset version is generated; incidental unblurred pixels in a background are not processed, not labelled and not retrievable from the weights. |
| **Biometric identification** | **None, and none possible.** The EU AI Act regulates biometric identification in the workplace heavily. This system performs no biometric processing whatsoever. Adding a `person` class would change that assessment completely and would require a fresh review before a single image was labelled. |
| **Consent** | Not required on the current design: no personal data is processed as the system's purpose, and no individual is identified, tracked or evaluated. Were the system ever pointed at an active construction site with identifiable workers, a lawful basis, worker notification and a DPA with every subcontractor would all be preconditions — per LS4, Section 3. |
| **Data retention** | Images are not committed to this repository. `data/` is gitignored; datasets are fetched at run time from their declared source. The repository holds weights, metrics and evidence renders only. |

## 3. Risk Statement

| Field | Entry |
|---|---|
| **High-impact False Negative** | A missed curtain-wall zone understates glazed area, understating both the envelope cost index and the Window-to-Wall Ratio. Consequence: the VE engine reports the envelope as cheaper and better-performing than it is, and the team does **not** open a package that should have been opened. The error is silent — nothing in the output signals the absence — which makes it the more dangerous of the two. |
| **High-impact False Positive** | A mirror-glass spandrel panel read as glazing overstates glazed area. Consequence: the VE engine recommends a glazing substitution against a ratio that was never real, sending the design team to re-engineer a compliant package. Cost: wasted design fees, a delayed programme, and credibility spent on a phantom. |
| **Which is worse here** | The false negative, because it is invisible. A false positive gets challenged the moment a human looks at the annotated image; a false negative produces a plausible number that nobody questions. This is the inverse of the PPE case in the slides, and it is why every evidence render in `results/evidence/` shows the boxes rather than only the numbers — the human check is the mitigation. |
| **Systematic risk** | Training data drawn mostly from mid-rise European commercial façades will under-perform on heritage buildings, vernacular construction and non-European envelope typologies. A cost index computed on such a building would be confidently wrong. Listed in the limitations statement below. |

## 4. Human-in-the-Loop

| Field | Entry |
|---|---|
| **Review process** | **Screening only.** Detections are a first pass that a qualified architect or cost consultant reviews before any figure reaches a client, a cost plan or a design decision. The VE assistant surfaces the annotated image alongside every number so the reviewer sees what the number was derived from. |
| **Who decides** | The project architect and the cost consultant, jointly. The model holds no authority and no veto. |
| **What is logged** | For every inference retained: source image, weights file and version, confidence threshold, timestamp, and the reviewing human. Per LS4, safety- and cost-relevant AI outputs must be reconstructable after the fact. |
| **Escalation** | Any detection driving a decision above the project's VE materiality threshold requires manual measurement from a scaled drawing before it is acted on — never from the image alone. |

## 5. Limitations Statement — when NOT to use this

**This model is an assistive tool for preliminary screening only. It produces False
Negatives. It must NOT be used as the sole verifier for life-safety decisions.**

Specifically, do not use it:

- **For quantity take-off or cost certification.** Outputs are uncalibrated pixel areas.
  Without a known scale, a reference dimension or camera calibration they are not square
  metres and cannot become square metres. Every VE read-out carries this basis string in
  its JSON.
- **For regulatory or code compliance**, including thermal, daylight or egress checks. It
  cannot measure a ratio in real units, so it cannot evidence compliance with one.
- **As a BIM-vs-reality verifier.** That requires camera pose, image registration and a
  reference model. None is implemented.
- **On heritage, vernacular or non-European façade typologies**, or on imagery unlike the
  training distribution — night, heavy rain, fog, extreme obliquity, fisheye or heavily
  scaffolded buildings. Performance there is unmeasured, which is not the same as adequate.
- **On any element below roughly 8 px**, where the information is not in the pixels.
- **For anything involving people.** No person class exists. It is not a safety monitor,
  not an attendance system and not a surveillance tool, and it must not be repurposed as
  one without a fresh governance review.

**Screening vs certification** (LS4, Section 3): this model *screens* façade images so a
human can prioritise attention. It *certifies* nothing.
